**Key build finding: Kokoro's `create_timed` returns phoneme timings, and the phoneme stream contains space separators between words.** So word-level alignment is a split, not an ASR pass — faster-whisper is dropped from the primary path entirely (~1 GB RAM and a model download saved). espeak cliticises function words ("on the" → one group) and splits compounds ("YouTube" → two), so `align.py` runs a small monotonic DP allowing 1:1, 2:1 and 1:2 matches. That took the test script from 6/10 to **10/10 paragraphs exactly aligned**.

**Measured on this box:** voice 2.95x realtime, 768 MB peak → a 12-min narration takes ~4 min. Architecture forced by 5.85 GB RAM: **Remotion renders only short alpha overlay clips; FFmpeg composites everything** — never a full timeline in Chromium.

**Phase 2 findings.** Pexels relevance is far better than Pixabay's - Pixabay returned a kingfisher for "empty office at night", so it is fallback-only behind a tag-overlap guard, plus `isAiGenerated`/`isLowQuality` filters. Pexels quality labels lie (a file tagged "uhd" measured 2560x1440) - select by pixel width. The cut planner scores boundaries by silence + punctuation and **penalises cutting after function words**; a hard 3s floor once discarded a clean clause boundary missing it by 0.02s and cut after "a" instead, so the window is graded, not absolute. Compose is two-pass by design: per-shot segments (sequential, cached, resumable) then concat demuxer with **stream copy**, so the segment encode is the only encode and twenty decoders are never open at once.

**Loudness matters:** raw Kokoro narration measured **-27.2 LUFS**. YouTube normalises to ~-14 and only attenuates, never boosts, so unnormalised output plays quiet against the feed. `loudnorm` in the mux brings it to -15.5.

**Measured per 83s video:** voice 28.4s/768MB, assets 62.8s/61MB, compose 4.9s/97MB - all far under the 1500MB budget. Extrapolates to roughly 9-10 min total for a 12-minute video.

**Footage quality — the "generic stock" fix.** Always taking the #1 search result is *why* footage reads as generic: for any common query the top hit is the single most-used clip on the internet. `score_candidate` now penalises rank 0 outright (every shot then came from result 2+). Also added a saturation penalty — rewarding colour contrast alone dragged selection toward neon outliers (a magenta gaming rig beside a documentary interview). **Known limit:** Pexels `avg_color` averages the whole frame, so a dark room with localised neon still reads low-saturation and slips through; only visual review catches it. Hence `fvs contact` (contact sheet, numbered tiles, seconds to render) and `fvs swap <shot> <n>` using alternates stored in the shotlist — no re-search, no quota.

**Segment cache must key on asset identity, not duration.** A swapped clip keeps the same duration, so duration-only caching silently reuses the segment rendered from the old footage. Fixed with a sidecar `seg_NNN.json` holding `asset_key` + `duration`.

**`nlm` CLI (notebooklm-mcp-cli 0.9.13, MIT).** Installs `nlm.exe` + `notebooklm-mcp.exe` into the per-user Scripts dir, usually NOT on PATH — `config.nlm_path()` resolves it rather than editing PATH. Create: `nlm <type> create <notebook_id> "<desc>" -y -j`. **`nlm` CLI traps, all verified the hard way (2026-08-20):**
- **Exits 0 on failure everywhere.** `login --check` prints "Authentication failed" and returns 0. Never branch on exit code; match output text and fail closed.
- **A profile row can exist while its credentials are invalid** (`default: (invalid)` while login is still pending). Parsing `login profile list` gave two false positives. Use `login --check` and require its success marker.
- **`notebook create` returns `notebook_id`, not `id`.** Persist it immediately — the notebook exists remotely before the rest of the stage runs, so a later failure otherwise creates a duplicate on retry.
- **`source add NOTEBOOK_ID -u URL` — the source is an OPTION, not positional.** `-u` repeatable for bulk, `-f` for files, `--wait` to block on processing.
- **Every artifact type has a DIFFERENT create signature.** Only `data-table create ID "description"` takes free text. `report create ID --format "Briefing Doc"`, `infographic create ID --focus ... --orientation landscape`, `mindmap create ID -t title`. No uniform axis exists; an explicit per-type mapping is the honest fix.
- **`mindmap create` is broken server-side** — "API error (code 3): INVALID_ARGUMENT" even with zero arguments. Moved to opt-in.

**Windows encoding, both directions (bit us twice):** `subprocess.run(text=True)` decodes with cp1252, but this CLI emits UTF-8 box-drawing and check marks — the mismatch raises inside subprocess's reader thread, leaving stdout EMPTY so every command looks like a silent failure. Pass `encoding="utf-8", errors="replace"`. Separately, printing that output to a cp1252 console raises `UnicodeEncodeError`, so `cli.main()` reconfigures stdout/stderr to UTF-8. Same class of bug killed the first Kokoro phoneme print.

**Two bugs found by measuring, both mine:**

**Packaging doctrine (2026-08-20).** Title and thumbnail must ask DIFFERENT questions: title states the fact (numbers lift CTR 20-30%, more than power words' ~7%), thumbnail opens the gap. A thumbnail that restates the title adds nothing — that was my error on roman-concrete. Power words work but the honest magnitude is **~7% / 1-2 percentage points, not "double"**; restraint (one or two) beats stacking. Curiosity gap is only legitimate when the video RESOLVES it — an unresolved gap is clickbait and lands back in inauthenticity territory.

**Title must match the COLD OPEN, not the best moment.** Steepest retention drop is 0:00-0:15 as viewers check the video delivered what they clicked. A title promising a payoff that arrives at 2:10 buys a faster bounce, not a better video. Also: never cherry-pick the favourable end of a range for a punchier title ("Ours Lasts 50" from a script that says "fifty to one hundred" - used "Ours Fails in Decades" instead). Keep titles under ~60 chars for mobile truncation.

**LRA CORRECTION — I compared the wrong things (2026-08-20).** The "documentary narration runs 6-12 LU" benchmark is a **programme** figure (voice + music + effects + inter-scene contrast). **Speech-only tracks normally measure 3-6 LU.** Our voice track at 3.7 LU is NORMAL, not defective. Do not chase voice-track LRA.

**Why loudnorm always compresses here (measured, not guessed):** narration is **-26.7 LUFS integrated with -2.4 dBTP** — a ~24 dB crest factor. Reaching -14 LUFS needs +12.7 dB, which would put peaks at +10 dBTP, so loudnorm reports `Normalization Type: Dynamic` and compresses regardless of `linear=true`, the target level (-14/-16/-18/-20 all tested), the LRA target (11/7/6/5 all tested), or passing real first-pass `measured_*` values. Control proving the mechanism: a plain `volume=10dB` preserves LRA (6.2 -> 5.9). A static-gain-only approach is not viable either — the TP ceiling caps usable gain at +0.9 dB, which would leave the video at -25.8 LUFS.

**Consequence: programme dynamics MUST come from music + SFX + silence, not from the voice.** This makes sound design the principled next step rather than a nice-to-have.

**PLACEMENT is the whole game — cues must land in PAUSES, not at the card.** First attempt placed cues at `shot.start + delay`; measured effect on the mix was **0.0 to -0.3 dB — completely inaudible**, because shot starts coincide with a word beginning. Levels that work against ~-20 dB narration: impact -8.5, tick -17 to -19, riser -29.6.

**Beware confounded audibility tests.** Comparing full mixes at cue times gave a *negative* delta for an impact, because adding energy changes the gain loudnorm applies to the whole programme. Measure the effects track in isolation, or in a window that is genuinely silent in the control.

**THREE bugs found by measuring, all mine:**
- **Silent-zero on throttle:** a `for...else` returned `[]` before the diagnostic print, making a rate-limited search indistinguishable from "nothing matched". Now raises `RateLimited`. This is the exact failure mode I keep warning about, written into fresh code.
- **`zoompan` d=<frames> multiplies duration by itself.** It emits `d` output frames for EVERY input frame, and a looped still supplies one per output frame — a 4s push rendered as **400s / 131MB**. Use `d=1` and drive zoom by `on` (output frame number).
- **`-loop 1` defaults to 25 fps**, so `-t 4` gives 100 frames tagged at 30 → 3.33s. Insert `fps=30` BEFORE zoompan. After both fixes: 4.00->4.00s, 5.70->5.73s (within a frame).

## Reference-informed generation: the legal line, researched (2026-09-02)
User asked whether we can show Gemini a real photo and have it recreate the subject. Researched rather than asserted, and the answer is YES with one bright line.
- **OLG Dusseldorf, April 2026** (directly on point): pure machine output is not copyrightable absent human creative control, AND a photograph's **abstract motif "sits in the public domain and can be reconstructed by generative systems, so long as the original's specific creative elements are not copied"** - recognisability of the same dog/setting was NOT itself copying. **US law**: idea/expression dichotomy + substantial similarity - the plaintiff must show appropriation of "the particular means of expressing an idea, not merely that they expressed the same idea".

"Show this subject accurately, your own composition" takes the idea = fine. `gemini_web.REFERENCE_RULE` states this in every referenced prompt: study for factual accuracy only, do NOT reproduce composition/framing/viewpoint/lighting.
