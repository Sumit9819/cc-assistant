# Evidence and reliability — 0.84.0

Use `verified_page_audit(post_id)` to assess a published page. It fetches a new response and applies fixed rules. Findings include rule IDs, observations and interpretations; sources include URL, UTC time, HTTP status, body fingerprint, cache state and collection scope. `unknown` means evidence is missing; `review` needs human context; a `pass` covers only that rule. There is no overall SEO certification or Google score.

HTTP errors, redirects, recognized CAPTCHA, non-HTML responses, storage failures and cache HITs cannot establish a usable current audit. Missing cache headers remain unknown: a new request does not prove the newest origin content. After-apply verification requires an observed cache MISS. Every capture invalidates the previous capture's verification. Incomplete inventories cannot prove absence.

Link verification preserves origin, scheme, port, query, fragment and trailing slash, resolves relative links and respects an observed HTML base URL. Similar paths on different domains cannot verify each other. Empty metadata expectations and unresolved SEO templates such as `%title% %sep% %sitename%` are inconclusive. Literal metadata expectations retain the full requested text; generated template output needs a separately resolved expectation or human comparison.

WordPress enforces evidence at the shared proposal queue for REST clients. Successful `whoami` is required within ten minutes. Each existing published target needs a usable `verified_page_audit`; unpublished posts and Elementor templates need full `get_post(slim=false)`; active Kit edits use `get_kit_settings`. Generic plugin-setting changes require `get_plugin_settings` to have observed the exact option. Receipts belong to the WordPress user and Application Password UUID or browser session, are stored by the server, and cannot be submitted by the model. Failed newer page observations invalidate older proof. Drafts created in the same request are an explicit exception to reading a post before it exists.

Page state must still match when drafting and approving. The environment fingerprint covers WordPress, active plugin/theme and MU plugin versions, active Kit settings, and selected URL, indexing, SEO and language configuration. It does not hash every file, setting or external service. Approval rejects changed evidence before claiming the pending row. Ten minutes limits observation age when proposing; review may happen later if state still matches. Since 0.89.4, independent supported edits can continue after sibling approvals, including across requests, only when version-2 recovery snapshots prove an unbroken sequence of exact approved changes with no overlapping targets. The original observation stays intact. External changes, unexpected hook writes, missing history and structural changes require fresh proposals. verify_change reports the evidence check separately from lint. The tested 0.89.3-to-0.89.4 patch can preserve the prior environment fingerprint only when every other fingerprinted value still matches. There is no force override.

Receipts apply to new REST proposals. Historical pendings and internal cron/CLI proposals do not acquire a client-session receipt retroactively; existing conflict/recovery checks remain. Recreate old work for stronger binding. Non-page changes require identity but do not automatically acquire a comprehensive audit of taxonomies, redirects or every dependency. Local Claude hooks remain an additional guard. The plugin cannot constrain unsupported statements in model prose.

Elementor controls come from the running widget registry. Shared validation covers widget updates/additions, nested container children, section rebuilds/replacements, full imports, accordion additions, composed/cloned drafts and publication. Repeater fields are checked recursively. Principal drafting/build previews, queueing, approval and final tree writes reject unsupported keys, enum values, ineffective gates and unavailable schemas. Changed settings are checked; untouched legacy values do not block a surgical edit. Publishing validates the complete tree. This does not prove every slider shape, dynamic tag, global token, third-party custom control, visual result or license entitlement.

Elementor tree writes read saved data back before reporting success. Rollback restores old widget settings exactly, removing keys introduced by the change. Restoration uses an internal path so newer control schemas cannot prevent restoring prior data; structural checks and readback remain. Proposal storage errors propagate through callers instead of producing a successful-looking pending ID.

Approvals and rollbacks share a named database lock per site. A busy or unavailable lock returns an error before claiming a proposal. Locks are released on ordinary exit and when MySQL ends the database session. Unrelated WordPress editors and third-party plugins do not share this lock; fingerprints and readback remain necessary. See [MySQL locking functions](https://dev.mysql.com/doc/refman/8.0/en/locking-functions.html). Deployment needs `GET_LOCK`/`RELEASE_LOCK` support; SQLite replacements and database routing proxies require separate compatibility work.

`get_plugin_settings` reports version, observation time and incomplete capability evidence. Storage ownership remains heuristic. Existing unregistered leaves are `storage_path_observed`, with feature effect unknown; new keys require an explicit registered schema. Rank Math, Polylang, Elementor Pro and Speed Optimizer still need broader, version-tested adapters for feature-level planning. A storage receipt proves an observation, not that a feature works.

Keep SEO evidence layers distinct: stored configuration, current server HTML, browser rendering and Google's indexed copy. Google explains that its [URL Inspection API](https://developers.google.com/search/blog/2022/01/url-inspection-api) provides indexed information rather than a live-page test. Search Console, field performance, JavaScript behaviour, visual layout and content accuracy are not established by this HTML audit. Local SEO scores remain heuristics.

Validation: 33 standalone PHP suites, hook regressions, PHP syntax, offline MCP discovery and 35 disposable WordPress/MySQL/Elementor integration checks. The runtime fixture uses WordPress 6.9.4, Elementor 4.0.4 and MySQL 8.0.35, with controlled page HTTP responses. It exercises real REST hooks, queues, approval, rollback and separate database connections. It does not replace production-version testing, a live SiteGround request or browser rendering. Previously observed production Elementor 4.2.3/Pro 4.0.2 and Rank Math 1.0.276 were not exercised by this local fixture.


## 0.89.5: WordPress runtime job flags

WordPress `_publish_post_hook` adds `_pingme`, `_encloseme` and `_trackbackme` during published-post saves. Cron removes them. These exact three keys are scheduling markers and are excluded from content fingerprints. The actual `enclosure` metadata, similarly named keys, SEO metadata, authors, content, permalinks and taxonomy assignments remain protected. Existing 0.89.3/0.89.4 hashes are compared against bounded legacy job-flag variants without editing saved evidence. Unsupported legacy flag multiplicities may fail closed.

`verify_change.evidence_check.diagnostics` now identifies proof failure reasons and, where derivable, field/meta/taxonomy names. Comparisons are the predicted state after a named approved change versus current state; later approved changes may explain differences. A passing preflight does not execute WordPress save hooks or prove future batch success. Do not repeat a requeue cycle without inspecting the cause. Production checks after installation are still required.

Core references: https://developer.wordpress.org/reference/functions/_publish_post_hook/ and https://developer.wordpress.org/reference/functions/do_all_pingbacks/ .
